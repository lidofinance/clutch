# Roadmap

A phase starts after the previous phase's gates close. Dates apply only when an external process sets them.

| Phase | Work | Gate |
|---|---|---|
| 0. Decisions | Accept design ADRs 005–011, 013 and 014, and process ADR 012; EM has accepted setup ADRs 001–004. Close or defer open decisions. The vendor's written confirmation of no standing approvals is due before a top-up above the launch cap, and its consent to be named before the mandate is posted (OD-54, OD-121). | EM accepts each ADR. Each open decision is closed or explicitly deferred. |
| 1. Specification | Write architecture, roles matrix, permission model, threat model and monitoring specifications. Give each invariant an ID. Keep the constellation policy, its compiler, its artifact and the fork tests in line with the accepted ADRs (OD-33). Set up the Lido Zodiac workspace (OD-35). Write the control matrix and screening rule list (OD-39, OD-45). Send the screening vendor its questions and the policy provider the UI requirements (OD-44, OD-84 to OD-88). Draft runbooks. Import the budget computation after mandate approval. | The acceptor accepts the specifications. Each invariant has an ID and names its ADR. |
| 2. Build | The round-trip check is built and runs on the rehearsal's vault; run it against the deployed vault, from its deployment block, before the first motion. The onboarding motion of each launch protocol, with its emergency exits through exit-governance (OD-49), and the motion that takes a token out of the orders account's lists are built and run on the rehearsal's vault. Still owed: the onboarding of Lido Lend's lender vault against the deployed vault (OD-132, OD-133). Top-up factories carry the funding (OD-140 to OD-144): the rehearsal registers them in the enabling vote and pays the launch tranche by top-up motions. Until the guard is set, a rule holds the launch cap (OD-145). Still owed for them: the alerts on a top-up motion. The factory takes raw writes (OD-134); its measures are in [its research note](docs/research/raw-factory-prototype-2026-11-12.md). The `motion` command turns a merged policy change into a motion's writes, and `motion-check` fails a motion that writes anything else; both run on the rehearsal's vault. Run them against the deployed vault once it exists, and have Lido's monitoring run `just watch`, the drift detector and the motion detector, on a schedule and page the emergency Safe on an alert (OD-136, OD-137). The command that computes each Safe batch's hash again, and checks each batch's calls against the policy, is built and runs on the rehearsal's batches (OD-92); run it on the published batches of the deployment before the vote. Build reporting, with the TMC-6 line for the whole treasury, the mandate's rule data, and the comparison of Lido's reading with the policy provider's (OD-84, OD-87, OD-111). Enforce invariant-to-test coverage and one-command verification. CI runs the fork suite, the round-trip check, the detectors' scenarios and the check of the rehearsal's Safe batches on `main` and in the merge queue, with the archive RPC key as the repository secret `MAINNET_RPC_URL`, and never on pull requests (OD-52); make the job a required check of the merge queue. | CI enforces a passing test for each invariant. One command verifies each permission change. |
| 3. Assurance | Audit the universal Easy Track factory, CoW's order signer, the policy and the deployment externally. The order signer has no known audit, so it counts as new code (OD-96). Lido reviews the guard's post-audit change before a top-up above the launch cap. Lido reviews the TWAP handler unless an audit covers it (OD-43). Drill each emergency and technical action on a fork. Check the LIP against the specifications. | Audit findings are closed or accepted. Each emergency drill starts its action within six hours. |
| 4. Governance and deployment | Publish the mandate on the forum and hold its Snapshot. Appoint the emergency Safe's fifth signer by Snapshot: a member of neither the committee nor the Emergency Brakes multisig (OD-58). Prepare the LIP and enabling on-chain vote, with the Safe batches published for review (OD-92). Rehearse the full vote, the batches and the launch tranche's top-up motions at a recent block (OD-92, OD-106; [enabling-vote spec](docs/specs/enabling-vote.md#the-full-rehearsal)). Repeat Safe release, advisory and bug-bounty checks shortly before the vote (OD-17). Deploy without the guard. The enabling vote registers the universal factory and the two top-up factories and pays nothing. After it, the committee's Safe creates the launch tranche's top-up motions, for one million dollars, which is the launch cap (OD-54, OD-55, OD-142). The Growth Committee transfers first-loss Earn shares to the first-loss Safe. | Safe checks find no change on the vault's paths, or EM decides again. A fork rehearsal of the vote verifies the orders account's CoW fallback handler, ComposableCoW domain verifier and relayer approvals. The vote passes. Deployed state matches the artifacts. |
| 5. Operation | Publish monthly reports and fortnightly cap readings on IPFS. Change budgets by motion only after an event (OD-56). Repeat drills. Before a top-up above the launch cap starts, set the guard on the committee's Safe with bypass mode off; the Zodiac UI requests the vendor's approval from that moment (OD-83, OD-121). Put the screening vendor's terms in place and complete Lido's review of the post-audit guard change. A top-up motion takes the vault above the cap only after the guard is set (OD-121, OD-142). Top up the vault by motion, within the registries' limits. | Continuous operation. |

## Standing gates

- **Hard gates:** the three gates of the [product brief](docs/product/brief.md#hard-gates), traceability, one-command verification and six hours, hold in every phase.
- Financial figures enter documents only if an attested computation produced them.
- Only EM or the Treasury Management Committee accepts ADRs.
